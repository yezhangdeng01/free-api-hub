# v1.0.7 发布说明

> 承接 PR #1（Anthropic Messages 协议翻译层）。自 v1.0.6 起 10 个 commit、15 个文件、+6940 / −941 行。
> 全量测试 **231 passed**（v1.0.6 是 161），零回归。

## 重点新能力

- **`/v1/messages`：Anthropic Messages 协议翻译层**。Claude Code、Anthropic SDK 这类只讲 Anthropic 协议的客户端，把 base URL 指向 `http://127.0.0.1:8787`、API Key 填网关 Token 就能用。客户端发的是 `x-api-key` 头（不是 `Authorization: Bearer`），网关两种都认。
  - 请求侧：`system`（字符串或块数组）、`messages` 的块数组（`text` / `image` / `tool_result`）、`tools` + `tool_choice`（`auto` / `any` / `tool` / `none`）、`stop_sequences`、`temperature` / `top_p` / `top_k`。
  - 响应侧：流式事件流 `message_start` → `content_block_start` / `content_block_delta` / `content_block_stop` → `message_delta` → `message_stop`；多轮工具调用的 `tool_use.id` ↔ `tool_use_id` 原样保留。
  - **`max_tokens` 必填**（协议如此）：缺了直接 400。不替客户端猜一个值——猜小了会把答案截断，而它看不到提示。
  - **`/v1/messages/count_tokens`**（原来 404）：下游是 chat 兼容渠道，没有 `count_tokens` 可透传，做法是按 `/v1/messages` 同一套翻译得到 chat body 再估它的大小（中文按字、其余按 4 字符约 1 token，图片按固定值）。量级够客户端判断上下文预算；要官方口径的精确值只能直连 Anthropic。
  - ⚠️ **不处理思考块**：Anthropic 的 `thinking` / `redacted_thinking` 块要求服务端签名，网关给不出合法签名，硬塞假块会被客户端判为协议错误——请求里的思考块忽略并记日志，上游推理内容也不译成思考块。要思考内容请走 chat 入口（那边是 `reasoning_content`）。
- **下游协议抽成 `dialects` 注册表**。内部形状永远是 chat completions，每种方言实现 `to_chat` / `convert` 两个函数，渠道路由、冷却分类、失败换路、会话粘性、用量记账**都不在方言层**。三种方言：`chat`（恒等映射）、`responses`、`messages`。加第四种 = 一个模块 + 注册表一行 + `main.py` 两行端点。`/v1/chat/completions` 也接上了注册表，让「三种入口一个形状」在代码里真正成立（副作用：请求体不是 JSON 对象时由 `to_chat` 挡成 400，旧写法是 `AttributeError` → 500）。

## 协议正确性修复（PR #1 合入后补的）

- **`stop_reason` 误判**：回包里明明有 `tool_use` 块，只要 `finish_reason` 缺失 / 是 `None` / 被渠道写成 `"stop"` / 编成不认识的值，就会报 `end_turn`——客户端据此认为这一轮正常结束，**工具静默地不被执行**。免额渠道漏 `finish_reason` 并不罕见，而这个网关恰恰是聚合这类渠道的。现在有 `tool_use` 块就以 `tool_use` 为准，但截断（`length`）优先——参数可能只写了一半，不该让客户端照着执行。流式与非流式统一走 `_stop_reason()`。
- **流式 `content_block` 顺序**：改成「开新块之前先关掉旧块」，每个块自己走完 `start → delta* → stop` 才轮到下一个。旧写法在并行工具调用时发的是 `start(1) start(2) stop(1) stop(2)`，工具之后再出文本时 `stop` 顺序与 `start` 相反，都不合 Anthropic 规范。官方 SDK 对此是宽容的（anthropic python 1.7 / `@anthropic-ai/sdk` 0.127 实测都能把内容拼回来），所以这不是「会不会崩」，是「守不守约」——也正因此只有测试能把这条不变量钉住。
- **回包 `model` 口径统一**：改为优先取上游返回值，与 `responses` 方言一致。同一个网关的两个协议入口不该对同一个字段给出不同答案。
- **错误体形状**：鉴权失败与 Host / 跨域拒绝这几条边缘路径，对 `/v1/messages` 改回 Anthropic 形状的错误体，不再回通用的 `{"detail": ...}`。
- **清死代码**：`_ANTHROPIC_ONLY`（定义后全文未引用）、回包上的 `anthropic-version` 响应头（那是请求头，官方响应里没有）。

## 合规与工程

- **第三方许可随包分发**（这是本次发版的主因）。v1.0.6 的包里**一份许可文本都没有**（09-22 下载 zip 逐条核对确认），根因是 v1.0.6 的 tag 指向 `9f561c8`，正是 PR #1 的 base，那次发版跑的是旧 `release.yml`。现在包内带 `LICENSE` + `THIRD-PARTY-LICENSES.md`（26 项依赖的许可与版权声明汇总，3604 行）。
- **清单集合口径修正**：原来按「跑脚本那台机器上装了什么」取集合，两个方向都会偏——装过 pyinstaller 的机器会把构建期工具一起列进来；依赖没装齐的机器则漏项（提交上来的那份只有 15 项，漏掉 `pywebview` / `pystray` / `pillow`，其中 **pystray 是 LGPLv3**）。改成从 `requirements.txt` 取根、按 `Requires-Dist` 求传递闭包，集合不再取决于本机装了什么。
- **CI 新增**（`.github/workflows/ci.yml`）。仓库原先只有 `release.yml`，触发条件仅 `push: tags: v*`，于是**任何 PR 都没有自动验证**，review 全凭人肉。现在 PR 与 push main 都跑 pytest + 许可清单同步校验（只比依赖集合、不比版本号——`requirements.txt` 全是 `>=`，拿版本号当失败条件会让 CI 周期性变红，而那种红不说明清单错了）。
- **修 Windows CI 控制台编码**：许可脚本打印进度会崩在 cp1252 上，脚本内强制 stdout / stderr 走 UTF-8。

## 已知限制

- **许可文本在包内 `_internal/` 目录下**，不在 zip 根目录。PyInstaller 6 的 onedir 会把所有 `datas` 收进 `_internal/`，spec 里写的 dest `.` 也不例外。合规上算随包分发，但从 zip 根目录看不出来——下一次发版会在包根再放一份。
